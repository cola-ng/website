# 对话流式响应

前端使用 `POST /api/learn/chats/{id}/send/stream`，请求格式与原有 `/send` 相同：

```json
{"type":"text","message":"Hello!"}
```

语音请求使用 `type: audio` 和 `audio_base64`。请求仍通过本站 Bearer token 鉴权，服务端先校验对话归属，再读取消息、调用提供方或写入记录。

响应为 `text/event-stream`。每个 `data:` 行包含 `event` 和 `data`：

| event | 用途 |
| --- | --- |
| phase | 语音识别等阶段提示 |
| accepted | 用户消息已保存，返回 `user_turn`、`ai_turn_id`，此时可清空输入框 |
| delta | 当前可显示的 `reply_en`、`reply_zh` 文本快照 |
| done | 文字与纠错已保存，返回完整 `user_turn`、`ai_turn` |
| error | 可显示给用户的错误，已经保存的消息和部分回复仍保留 |
| audio_start / audio_chunk / audio_end | 用户 TTS 音频段元数据、分片及段结束，带有序 sequence 和字节偏移 |
| voice_error | 语音失败，保留已生成的文字；不自动切换音源 |
| voice_done | 用户 TTS 模式的传输结束；done 仍只表示文字保存完成 |

两家提供方均调用原生流式接口。模型先输出英文回复，浏览器正确处理分块 UTF-8 和 JSON 转义字符，正常发送不轮询对话状态。文字完成后立即发送 `done`；TTS 在后台生成并更新音频路径，不阻塞文字。音频尚未就绪时，页面可使用浏览器朗读；刷新历史后可播放已经生成的音频。

刷新或离开后重新打开尚在生成的对话时，原 POST 流已经不存在。页面仅对历史中的 `processing` 消息每两秒检查一次已保存状态，完成后更新历史；网络失败或超过恢复期限时提示刷新，离开页面后停止检查。这条恢复路径不参与正常的流式发送。

原有 `/send` 仍返回 JSON，复用同一生成及保存流程，兼容旧客户端。它等待完整文字，也不等待 TTS。

## 语音交互与打断

网页对话保留手动录音，开始录音会先停止朗读、取消当前回复。另可点击“开启连续语音”：本地 AudioWorklet 输出单声道 16 kHz PCM、每帧 20 ms，WebRTC VAD 在本地检测说话；停顿约 1.3 秒后自动提交 WAV。录音最长 15 秒，短噪声不提交；未开始说话时只保留本地最近 500 ms 音频，确认开口后将它接在新录音前，保留开头。

连续模式默认使用用户在 AI 服务配置中启用的 TTS，包含该能力对应的服务商、凭据、模型和音色。对话页“语音设置”可显式选择“浏览器系统语音”，选择保存在本地；连续语音运行时禁止切换音源。用户 TTS 失败、禁用或音频无法解码时明确提示，不自动回退系统声音或平台服务。

用户 TTS 请求使用 `X-Conversation-Voice: provider`。服务端将稳定的回复前缀按完整短句合成，最长约 220 个字符；同时最多处理当前段与一段预取，按句序输出，每段完整合成后才下发该段音频，不宣称所有上游均支持字节级流式合成。SSE 音频按 24 KiB 分片发送，通道、句子队列、单段 2 MiB 与本轮总计 10 MiB 均有上限。此模式不额外合成整段缓存；浏览器按序解码播放，只有文字、语音发送和本地播放全部完成后才开始接话等待。打断会停止当前声源、清空待播分段、使迟到解码失效，并取消正在进行的合成与预取。

显式选择浏览器音源时使用 `X-Conversation-Voice: browser`，只在本地按短句朗读，不调用服务端 TTS。未提供输出头的旧客户端仍使用文字完成后生成整段后台录音的兼容流程。回复流和朗读均完成后进入接话等待，30 秒无人接话自动结束。Esc、结束按钮、切到后台、页面离开、麦克风断开或声音被系统暂停时会释放采集和播放资源。普通手动“朗读消息”继续优先使用服务端录音。

播放中直接开口打断需浏览器明确报告启用了回声消除，并通过 VAD 持续语音确认：播放开始保护约 200 ms，随后连续 8 帧语音（160 ms）；未播放时连续 6 帧（120 ms）开始录音。不使用单纯音量阈值作为播放打断条件。设备未确认回声消除时仍能点击“打断回复”。这些是交互参数，不包含浏览器采集、VAD、音响和系统调度的延迟。

每个网页流式请求带独立的 `X-Conversation-Request`（16–96 位英数或短横线）。主动打断调用 `POST /api/learn/chats/{id}/cancel`，JSON 为 `{"request_id":"原请求编号"}`；服务端校验登录和对话归属，只取消对应请求，等待旧生成退出和取消状态保存后返回。取消可以先于原始发送到达，同一编号短期内不能重放。未发送此头的旧客户端仍能生成回复。

取消中的助手消息保留最后一段文字，状态为 `cancelled`，不进入之后的模型上下文，也不生成未完成轮次的纠错。已完成的文字保留为完成状态，取消会停止其尚在进行的后台语音合成。前端同时隔离旧轮次的迟到响应、取消回调和朗读结束事件。普通文字/兼容客户端关闭 SSE 连接仍允许后台完成并在重新打开时恢复；用户 TTS 连续模式在连接关闭时取消该轮生成与合成，避免无人接收的语音继续消耗服务。

当前取消任务表位于单个 API 进程内，适用于现有单实例部署；若扩展为多实例，取消与发送必须路由到同一实例，或先引入共享取消通道。网页依赖浏览器 AEC，不包含 amigo 电脑桥中的 native SpeexDSP，也不包含 ESP32 的硬件 AEC/WakeNet；不应将合成音频回归视为真实房间外放声学验收。

上下文只读取当前用户、当前对话、当前消息之前最近的 40 条已完成消息，并限制总长度。每段对话同时只能生成一条回复；并发发送返回冲突，超过 5 分钟的遗留生成状态允许恢复。语音识别、生成回复、语音合成均有超时；提供方失败会返回错误，不再用一段固定道歉冒充成功回复。

## 模型与部署

用户启用的个人 AI 配置优先，配置失败时不会使用平台密钥。没有启用的个人配置时，仅已支付且订阅有效的用户可使用服务器的 `AI_PROVIDER_DEFAULT`；免费、试用及其他非付费用户需配置自己的服务。具体资格及接口见 [账户与 AI 说明](account-and-ai.md)。服务器通过 `ZHIPU_CHAT_MODEL` 指定平台模型；服务器环境变量修改后需要重启服务，个人配置修改则立即生效。

平台模型由智谱配置提供。模型是否可用应以真实生成请求为准，不能只检查模型目录列表。

Nginx 关闭 API 代理缓冲；SSE 返回 `Cache-Control: no-cache, no-transform`、`X-Accel-Buffering: no` 并定期发送保活注释。外层代理也应允许持续发送数据。

依据：项目锁定版本的 outfox Zhipu 流式客户端。

## 验证

隔离数据库测试覆盖上下文顺序、并发发送、逐段返回早于完成、TTS 不阻塞完成、失败时保留部分回复并允许再次发送。浏览器测试覆盖分块中文、生成过程的按钮锁定、正常发送无轮询、重新打开时恢复回复，以及历史翻页保留近期消息。外部模型和生产代理的实际耗时另外测量，不能用测试替身的耗时推断线上性能。

`tests/voice.py` 检查真实 HTTP 取消的鉴权、归属、请求乱序、立即开始下一轮和迟到取消。`chat_stream_database_flow` 另验证取消后部分文本持久化、上下文排除和旧生成不恢复。`tests/voice.cjs` 经真实 WASM 页面运行 AudioWorklet 和本地 WebRTC VAD，验证显式浏览器音源、偏好保存、WAV、接话和媒体释放；`tests/voice-provider.cjs` 验证用户 TTS 的实际音频解码/播放、段落顺序、播放打断、服务/解码/传输失败和无系统音源回退，并以本机真实 API/SDK/预览 SSE 代理完成一轮实际调用；由 `tests/browser.cjs` 和 `tests/run.ps1` 调用。输入 WAV 由 `tests/voice-fixture.ps1` 生成到 workspace 的正常 target 目录，不采集个人麦克风。
